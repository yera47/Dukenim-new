# Dukenim — полная архитектура продукта

**Версия карты:** 20 августа 2026  
**Назначение:** единый источник правды о продукте, технической схеме и результатах девяти этапов. Документ намеренно разделяет подтверждённые решения, готовый код, применённую production-базу и то, что ещё нельзя называть запущенным.

## 1. Что строит Dukenim

Dukenim — мультиарендная (multi-tenant) платформа для малого ритейла Казахстана. Она заменяет ручной путь «пост в Instagram → переписка → уточнение наличия → заказ в заметках» единым операционным контуром:

```text
Витрина магазина → самостоятельный выбор товара → заказ / бронь
                                        ↓
                 товары, остатки, клиенты и заказы → кабинет владельца / сотрудника
                                        ↓
                         здоровье платформы, тарифы, поддержка → Dukenim Root
```

Публичная формулировка, на которой строится сайт: **«Dukenim — продажи 24/7»** и **«Одна ссылка вместо сотни сообщений»**. Это не конструктор «сайтов за клик»: ценность в том, что покупатель выбирает и оформляет сам, а владелец управляет всем в одном месте.

География первого запуска — Казахстан; денежная единица — KZT, цены во всей системе хранятся целыми числами тенге.

## 3. Технологическая архитектура

### Клиент и сервер

- **Next.js 15 + React 19 + strict TypeScript.** App Router, серверные страницы, server actions и API routes.
- **Middleware** определяет контекст пользователя и ограничивает доступ к `/admin` и `/root`.
- **Supabase SSR-клиенты** разделены на browser/server/admin. Сервисный клиент используется только на сервере для операций, которым нельзя доверять из браузера.
- UI должен остаться доступным: нативные формы, понятные ошибки рядом с полем, рабочая клавиатурная навигация, реальные действия за каждой кнопкой. Декоративный UI не попадает в tab-order.

### Данные и доступ

- **Supabase Auth** хранит учётные записи; приложение никогда не хранит пароли самостоятельно.
- **PostgreSQL + RLS** — изоляция каждого магазина. Пользователь получает строки только своего tenant, а супер-администратор — только через явно проверенный серверный путь.
- Роли верхнего уровня: `customer`, `owner`, `superadmin`; роли внутри магазина: `owner`, `admin`, `staff`.
- Защита остатков строится не на прямом редактировании товара: каждое изменение проходит через `stock_movements`; триггер применяет изменение и блокирует прямую подмену stock.
- Критические многошаговые операции вынесены в RPC: создание первого магазина/онбординг, товара с вариантами, заказа витрины, офлайн-продажи, активация подписки.

### Интеграции

- **Vercel** — хостинг Next.js.
- **Cloudflare** — будущий авторитетный DNS и защитный периметр. Зона подготовлена, но NS ещё не переключены у регистратора.
- **Backblaze B2** — приватный зашифрованный bucket для резервных копий. Bucket создан, но ключ минимальных прав и расписание копий ещё не настроены.
- **GitHub + GitLab** — основной исходный репозиторий и независимое приватное зеркало. GitLab-зеркало пока не создано и первый push не выполнен.
- **Kaspi Pay / иной сертифицированный платёжный провайдер** — только будущая официальная интеграция. Dukenim не собирает логины или пароли Kaspi.
- **Email / push** — провайдеры должны быть подключены официально. До custom SMTP восстановление пароля нельзя считать production-готовым.

### Главные модели

| Модель | Ответственность |
|---|---|
| `tenants` | магазин, slug, статус, жизненный цикл каталога, тариф |
| `tenant_users` | связь сотрудника с магазином и его операционная роль |
| `tenant_settings` | контакты, доставка, возврат и рабочие настройки |
| `tenant_storefront_settings` | шаблон, палитра, акцент, публичный вид витрины |
| `storefront_templates` | четыре базовых семейства шаблонов и будущие версии |
| `categories`, `products`, `product_variants` | ассортимент, варианты размера/цвета/объёма, цена, наличие |
| `stock_movements` | неизменяемая причина изменения остатка: продажа, возврат, поставка, корректировка, списание |
| `customers`, `orders`, `order_items` | покупательский путь: онлайн, офлайн, заказ, состав и статус |
| `delivery_zones` | разрешённые способы, зоны и стоимость доставки |
| `subscriptions` | статус тарифа и период доступа |
| promotion / checkout / audit tables | промокоды, честные заявки на тариф до реальной оплаты, журнал действий Root |

## 5. Сквозные сценарии

### 5.1 Регистрация и первый запуск

```text
Регистрация: имя + бизнес + email + пароль + подтверждение пароля
→ аккаунт и нейтральные «7 дней полного доступа»
→ dashboard без выдуманных ограничений
→ «Создать каталог»
→ ниша + телефон + шаблон + палитра
→ черновик или продолжение
→ первый товар с ценой + способ связи
→ публикация витрины
```

Регистрация **не должна** незаметно создавать каталог. Жизненный цикл каталога: `not_started → building → ready`. До создания каталога добавление товара серверно блокируется. Владелец может пригласить контент-менеджера ещё до публикации, чтобы не наполнять каталог один.

### 5.2 Создание и публикация каталога

1. Владелец называет каталог и выбирает нишу.
2. Выбирает допустимый для тарифа шаблон и палитру; видит live preview до применения.
3. В «Бренд» сначала видит готовые палитры, затем может добавить безопасный фирменный акцент.
4. В «Старт» возможности «Бренд» видимы, но спокойно заблокированы с объяснением ценности, а не как внезапная ошибка.
5. Каталог можно сохранить черновиком.
6. Для публикации обязательны: название, минимум один товар с ценой и способ связи. Доставка/возврат необязательны и не отображаются покупателю, пока не заполнены.
7. После публикации шаблон и палитра меняются через preview-before-apply; адрес, товары и заказы не теряются.

### 5.3 Покупательский путь

```text
/s/[slug]
→ главная / категория / поиск / фильтры
→ карточка товара
→ вариант (размер, цвет, объём) и остаток
→ корзина
→ имя + телефон + доставка / самовывоз / бронь
→ способ оплаты при получении
→ заказ с номером и статусом «Новый»
→ немедленно в CRM магазина
```

- Покупателю не нужен аккаунт.
- Нет в наличии — купить нельзя.
- Если у товара нет вариантов, доступна быстрая кнопка добавления в корзину.
- Самовывоз и доставка показываются только если владелец их включил.
- На первом запуске честно показывается только оплата при получении: наличные, терминал/карта или Kaspi QR при выдаче, если магазин действительно это принимает.
- Не используется формулировка «перевод» как универсальная оплата и не имитируется онлайн-платёж.
- Бронь временно резервирует остаток, имеет срок действия, подтверждается владельцем и при выдаче одним действием превращается в офлайн-продажу.

### 5.4 CRM и офлайн-продажа

CRM объединяет заказы, брони, товары, клиентов, остатки и простую аналитику. Статусы заказа: `new → confirmed → assembled → delivering → done`, с отдельным `cancelled`.

Офлайн-продажа — это быстрый многопозиционный cart, а не форма «продать один товар»: сотрудник добавляет несколько товарных строк, выбирает размер/цвет, меняет количество и при необходимости прикрепляет клиента.

### 5.5 Тариф и промокод

```text
«Выбрать тариф» → период месяц / год → промокод
→ серверная проверка условий → сохраняется заявка на подключение
→ реальный провайдер оплаты (после подключения и проверки)
→ активация подписки
```

До подключения юридически подтверждённого провайдера нельзя показывать успешное списание денег. Промокоды создаёт только Root, они серверно проверяются, журналируются и по умолчанию не складываются друг с другом.

Тарифы не ограничивают сотрудников и базовую операционную работу. В интерфейсе разрешено показать будущую функцию, но нельзя скрытно ломать сценарий: блок должен быть визуально спокойным, объяснять, что откроется в «Бренд», и вести к понятному сравнению.

## 7. Сотрудники и права

Четыре предложенных позиции — готовые стартовые шаблоны, а не жёсткая оргструктура:

| Шаблон | Стартовый набор |
|---|---|
| Владелец | всё, включая доступ к бизнесу и команде |
| Менеджер | заказы, брони, клиенты, товары |
| Контент-менеджер | товары, фотографии, каталог, акции; без выручки и заказов |
| Продавец | офлайн-продажа, выдача брони, ограниченный каталог |

Владелец создаёт и свои должности, выбирает обычный шаблон или «с нуля», затем даёт доступ к модулям. Интерфейс прав имеет два уровня: простой выбор модулей и расширенный editor. Доступ можно изменить или отозвать в любой момент. Даже «полный операционный администратор» не получает права передавать владение, менять тариф/биллинг, подключать оплату или выполнять необратимые действия с аккаунтом.

## 8. Root — управление самой платформой

`/root` не смешивается с кабинетом магазина и открывается только `superadmin`.

- здоровье платформы, инциденты, резервные копии;
- жизненный цикл магазинов и воронка: регистрации, создание каталога, публикация, заказы;
- тарифы, feature flags, rollout шаблонов;
- промокоды и заявки на тариф;
- очередь поддержки через in-app/email;
- неизменяемый журнал чувствительных действий;
- в будущем — ограниченный оператор поддержки без владения, биллинга, платежей и необратимых прав.

Для смены тарифа, приостановки/восстановления магазина, экспорта данных и будущего impersonation требуется причина и запись в audit. WhatsApp не автоматизируется, пока нет совместимой официальной интеграции.

## 12. Строгий release gate: что нельзя пропустить

Публичный запуск запрещён, пока не закрыты все пункты ниже:

1. **Выкладка и E2E:** выложить текущий код; в браузере пройти registration → create catalog → product → publish → guest order → CRM → offline sale → root promo request.
2. **Checkout security:** после выкладки и smoke test применить `202608200002_restrict_guest_checkout_rpc.sql`, чтобы браузер больше не вызывал legacy SECURITY DEFINER RPC напрямую.
3. **Auth email:** настроить custom SMTP и включить leaked-password protection в Supabase Auth; проверить confirmation и password reset письма.
4. **Юридические реквизиты:** заменить шаблонные данные в оферте/политиках реальными данными ИП/ТОО, БИН, адресом, контактами, реквизитами и подписантом; провести юридическую проверку.
5. **Оплата:** не включать online payment до регистрации бизнеса, договора/проверки провайдера и успешного sandbox/production test. Пока — только заявка на тариф и реальные способы при получении.
6. **Backups:** создать scoped B2 application key, сделать encrypted DB/storage backup jobs, retention, restore drill и журнал результатов.
7. **DNS:** завершить GitLab mirror до DNS-изменений; при готовности сменить NS у Hoster.kz на Cloudflare после проверки DNSSEC и всех mail records.
8. **Наблюдаемость:** error tracking, uptime, cron monitoring, алерты по backup/checkout и понятная incident procedure.
9. **Mobile:** до заявления «полноценное приложение» реализовать real iOS/Android client с тем же backend, RLS, permissions, push и barcode scan.

## 14. Принципы дальнейшей работы

1. Не смешивать **решение**, **локальный код**, **applied migration** и **работающий production flow**.
2. Любая кнопка должна иметь реальное действие, loading/error/success-state или не быть кнопкой.
3. Новая функция сначала проходит tenant/RLS/permission/stock/audit review, затем UI.
4. Новая визуальная система сначала проектируется в Figma, после выбора — переносится в код целым слоем без каскада временных CSS-исправлений.
5. Не обещать клиенту интеграции, hardware или онлайн-оплату до подтверждённой технической и юридической готовности.
6. После любого релизного изменения: TypeScript → build → production smoke test → обновление `AI_HANDOFF.md`.
