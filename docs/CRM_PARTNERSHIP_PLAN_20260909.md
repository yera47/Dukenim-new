## 2. Что должен уметь обмен

Это желаемый контракт, не заявление о поддержке всеми поставщиками. Для CRM без товароучёта достаточно контактов, сделок и статусов; складские данные получать из учётной системы магазина.

| Данные | Из внешней системы в Dukenim | Из Dukenim во внешнюю систему |
|---|---|---|
| Подключение | ID аккаунта/организации, разрешённые магазины/склады, валюта, часовой пояс, права | ID подключения и сопоставление конкретного магазина |
| Каталог | Внешний ID товара и варианта, SKU, штрихкод, категории, название, описание, единицы, размер/цвет/объём, доступные изображения | Только согласованные изменения полей, если магазин выбрал Dukenim источником этих полей |
| Цены | Тип цены, обычная и акционная цена, валюта, налоги и период действия | Применённые к заказу цены и скидки; изменение справочника только при согласованном управлении |
| Остатки | ID склада, физический остаток, резерв, доступное количество, дата/версия | Запрос резерва/отпуска/освобождения, если API это поддерживает |
| Заказ | Внешний ID, принятие/отказ, сопоставленный статус, изменения исполнения | Уникальный ID заказа, время, позиции с вариантами, количество, цены, скидки, доставка, итог KZT, комментарий |
| Клиент | Внешний ID и минимальные нужные изменения в рамках разрешения магазина | Имя, телефон, email при наличии, сведения для исполнения заказа |
| Доставка/самовывоз | Статус, трек, время готовности, идентификатор точки при наличии | Метод, адрес или точка, стоимость и согласованные условия на момент заказа |
| Оплата | Учётный статус и внешний ID операции, если есть надёжное происхождение | Подтверждённый платёжный статус, сумма, ссылка на транзакцию без данных карты |
| Отмена/возврат | Причина, позиции, количество, сумма и статус исполнения | Запрос отмены/возврата и освобождения резерва в рамках доступных функций |
| Себестоимость | Опционально: метод, значение на дату продажи/партии и источник | Обычно не требуется; доступ отдельно от публичного каталога |
| Лояльность/аналитика | Опционально разрешённые правила и баланс | Источник заказа и UTM при наличии; маркетинговое согласие не выводить из факта покупки |

Не импортировать по умолчанию всю клиентскую базу, переписку или кадровые данные. Не передавать ключи эквайринга в CRM. Заказы и остатки сопоставлять по ID, а не названию. Деньги и единицы количества преобразовывать явно: внешние системы могут использовать другую точность; несовместимые данные отклонять, а не округлять молча.

## 3. Кто главный при синхронизации

- Для каждого магазина отдельно выбрать источник каталога, цен, остатков и статусов.
- Предложение по умолчанию для магазина с учётной системой: учётная система управляет ценами/остатками; Dukenim — дизайном и публичными текстами; интернет-заказ рождается в Dukenim, дальше отправляется в выбранную систему.
- CRM и учёт могут подключаться одновременно, но не должны дважды списывать товар. Назначить ровно одного исполнителя складской операции и хранить её внешний ID.
- Изменения остатков в Dukenim должны проходить через stock_movements, включая корректировки при сверке.
- Статус сделки «успешно» не является доказательством банковской оплаты. Состояние платежа, исполнения заказа и возврата денег хранить раздельно.
- Версионирование событий, защита от дублей, очередь повторов, журнал ошибок, периодическая сверка, контроль устаревших остатков и отзыв доступа обязательны в будущем адаптере.

## 4. Что запросить у каждой платформы

### Технический пакет

1. Документация API/OpenAPI, поддерживаемая production-версия, changelog.
2. Регистрация разработчика и тестовый аккаунт с двумя независимыми тестовыми магазинами.
3. OAuth или отдельный токен магазина, scopes, срок жизни, обновление и отзыв доступа. Ключ приложения не равен доступу ко всем клиентам.
4. Матрица методов read/create/update и событий для таблицы выше; явно указать неподдерживаемое.
5. Вебхуки: аутентичность/подпись, повторы, порядок, ID событий, восстановление пропущенных изменений. Если их нет — разрешённая частота опроса.
6. Лимиты запросов, пагинация, массовый импорт, фильтр updated_since, версии записей, ошибки и идемпотентность.
7. Семантика остатков/резервов, конкурентного заказа последней единицы, отмены и частичного возврата.
8. Внешние ID и поиск по ним, пользовательские поля, таблица статусов, единицы денег/количества и часовые пояса.
9. Возможность работать с несколькими независимыми аккаунтами, требования к публикации приложения и минимальные тарифы клиентов.
10. Технический контакт, сроки ответа, политика прекращения старых API и уведомления об изменениях.

### Коммерческий пакет для обсуждения (не юридическое заключение)

- Нужен ли отдельный договор для API, Marketplace и партнёрства или достаточно опубликованных условий?
- Стоимость API, приложения и поддержки; кто кому платит, есть ли лимиты по магазинам.
- Допускается ли наш сценарий конструктора магазинов и массовое подключение клиентов с их разрешения?
- Условия обработки/хранения/удаления данных и распределение обязанностей; перед подписанием проверить применимость с юристом.
- Право упоминать интеграцию и использовать логотип, размещение в каталоге, совместные материалы.
- Пилот, контактные лица, критерии приёмки, сопровождение, прекращение сотрудничества и отключение магазинов.
- Реферальная модель или revenue share обсуждаются отдельно; не обещать эксклюзивность, объём клиентов и гарантированные продажи.

## 6. Реестр переговоров и пилот

Для каждой компании фиксировать: официальный канал, контакт/роль без приватных сведений, дату обращения, ответ, ссылку на API, sandbox, модель доступа, методы, тарифы, договор, следующий шаг и статус. Сейчас обращения в рамках этого исследования не отправлены.

Предложение: первые переговоры Rosta, amoCRM, Битрикс24, МойСклад, UMAG; затем RetailCRM, Paloma365, BILLZ, Poster и локальный интегратор 1С. Реализацию начать с одной CRM и одной учётной системы после подтверждения условий и спроса, не со всех одновременно.

Пилот проверяет: авторизацию двух магазинов без смешения данных; импорт вариантов и цен; обновление остатка; один заказ без дублей при повторе; корректную отмену/резерв; статусы; отказ API и повтор; отзыв доступа; отсутствие секретов в логах. Это план проверок, не результаты уже проведённых тестов.

## 7. Позиционирование без конкуренции

Короткая формулировка для всех переговоров:

> Dukenim — не замена CRM, ERP или кассовой системе. Это управляемая публичная витрина и канал интернет-заказов для малого бизнеса Казахстана. После подключения выбранная система партнёра остаётся рабочим контуром и источником истины для сделок, товаров, остатков или ресторанных операций — в зависимости от её назначения.

Не использовать в первом письме формулировки «собственная CRM Dukenim», «перенесём клиентов к нам», «заменим ваш интернет-магазин» или «нам нужен общий API-ключ». Не обещать число клиентов, выручку, эксклюзивность или уже готовую интеграцию. Правильный запрос: согласовать технологическую модель, получить developer/sandbox-доступ и разработать пилот.

Предлагаемая модель подключения:

1. В Dukenim владелец магазина нажимает «Подключить [систему]».
2. Система партнёра показывает собственный экран авторизации и перечень прав.
3. Администратор конкретного аккаунта разрешает только нужные scope.
4. Dukenim хранит отдельное подключение конкретного магазина; доступ можно отозвать с обеих сторон.
5. Если OAuth отсутствует, предприниматель создаёт отдельный ограниченный API-ключ в своём аккаунте. Общий ключ партнёра не заменяет разрешение магазина.

### Решение по 1С

Центральную рассылку «в 1С» пока не делать. У 1С нет одного SaaS-аккаунта и одного универсального API-разрешения для всех клиентов: подключение зависит от конфигурации, версии, публикации OData/HTTP-сервисов и доработок конкретной базы. Правильный путь позже — выбрать одного казахстанского 1С-интегратора, согласовать поддерживаемые конфигурации (Розница/УТ/УНФ для Казахстана), выпустить проверяемый коннектор и только затем масштабировать через партнёрскую сеть.
