# Оплата товаров в Dukenim: решение для реализации

Проверено 9 сентября 2026 года. Область: казахстанские магазины физических товаров, деньги поступают конкретному продавцу. Это не оплата подписки Dukenim и не предложение принимать деньги магазинов на наш общий счёт.

## Рекомендация

Первым техническим кандидатом выбираю **FreedomPay, платёжную страницу Merchant API**. Резервный путь — **Halyk ePay**, особенно для уже подключённых к нему магазинов. Это инженерная рекомендация по изученным протоколам, а не заключённый договор и не доказательство самого быстрого прохождения проверки бизнеса. Стоимость, сроки оформления каждого мерчанта, поддержка платформенной модели и возможность автоматизации подключения требуют письменного ответа провайдера.

Kaspi оставляем отдельным каналом: обычную ссылку нельзя превращать в подтверждённый эквайринг выдуманными параметрами. Нужен доступ к официальному продукту интеграции.

## Что подтверждают первоисточники

| Вариант | Подтверждено | Ограничение для Dukenim |
|---|---|---|
| FreedomPay | Merchant API принимает сумму/валюту, номер заказа, адрес результата и страницы возврата. Есть тестовый режим и подписи | Нужны оформленный аккаунт продавца и его доступы. Наличие API не означает готовое автоматическое подключение каждого клиента |
| Halyk ePay | Платёжная страница, сумма, возврат, `autoBackLink`, серверное уведомление и проверка статуса | Банк выдаёт TerminalID, ClientID, ClientSecret; нужны согласование и тесты |
| CloudPayments Казахстан | Официальный сайт описывает виджет, платёжные ссылки, Apple Pay/Google Pay | Казахстанская документация разработчика при проверке ответила 502. Российский протокол не считаем подтверждением полной совместимости казахстанского договора/API |
| Kaspi, обычная ссылка | Покупатель сам вводит сумму в приложении | Нет подтверждённого параметра суммы и callback именно для этой ссылки |
| Polar | Merchant of Record со своими ограничениями | Правила запрещают физические товары и marketplace-схемы; не подходит для оплаты товаров наших магазинов |

Halyk: [платёжная страница](https://epayment.kz/docs/platezhnaya-stranica), [документация](https://epayment.kz/docs). CloudPayments: [официальный сайт Казахстана](https://cloudpayments.kz/), [казахстанская документация](https://developers.cloudpayments.kz/). ### Почему нельзя просто добавить сумму к ссылке Kaspi

Официальная инструкция обычной удалённой ссылки прямо предусматривает самостоятельный ввод суммы покупателем. У Kaspi есть отдельный интеграционный протокол платежей для дистрибьюторов, где используются идентификаторы сервиса, предоставленные Kaspi, и параметр суммы. Это другой договор/продукт, не разрешение дописать `amount` к любой ссылке `pay.kaspi.kz/pay/...`. [Инструкция интеграции](https://guide.kaspi.kz/cdn/content/pay/product/documents/Instrukciya-po-integracii-1C-s-servisom-Platezhi-na-Kaspi-kz-dlya-distribyutorov.pdf?ri=70005143-a17b-414e-8ab3-5410f83360f5), [партнёрство](https://kaspi.kz/webpay/partnership/kz).

Возврат на наш сайт и нажатие «Я оплатил» не подтверждают деньги. Автоматическое заполнение интерфейса приложения, доступ к SMS/паролю или неофициальный агрегатор не выбраны как основа интеграции. Без официального подтверждения нельзя автоматически переводить заказ в «оплачен».

## Как подключение должно выглядеть для продавца

1. При сборке: доставка/самовывоз, затем «Оплата». Доступна явная кнопка выбора «Подключу позже».
2. При выборе провайдера сохраняем предпочтение, но не включаем кассу. Не просим секреты в чате поддержки.
3. Продавец оформляет бизнес-аккаунт у провайдера. Dukenim показывает статус: оформление → доступы → тест → готово. Нельзя обещать OAuth, если провайдер не подтвердил партнёрский onboarding API.
4. Доступы поступают через отдельный защищённый серверный механизм. Секреты не в публичной таблице, браузере, журнале или URL. Ключ привязан к tenant, доступ — только серверу.
5. Проверяем сумму, валюту KZT, merchant/order ID, повторные callbacks, неуспешную оплату и возврат. Только после этого доступен оплачиваемый checkout.

## Обязательные технические свойства адаптера

- Сервер заново считает корзину из реальных цен и вариантов. Не принимает сумму из браузера как достоверную.
- Платёжная попытка связана с конкретным продавцом, заказом и суммой; повтор запроса не создаёт повторное списание.
- Подпись и серверный статус проверяются по протоколу выбранного провайдера. Несовпадение суммы/валюты/магазина никогда не активирует заказ.
- Для FreedomPay обрабатываем повторную доставку Result URL идемпотентно. Для Halyk используем документированную проверку статуса и `secret_hash`. [FreedomPay](https://freedompay.kz/docs/merchant-api/pay), [Halyk](https://epayment.kz/docs/platezhnaya-stranica).
- Истечение ожидания оплаты освобождает резерв ровно один раз. Поздняя оплата после истечения — отдельный случай сверки, не повторная автоматическая продажа отсутствующего товара.
- Возврат отражается отдельно от отмены заказа. Не называем внутреннюю отмену банковским возвратом.
- Карточные реквизиты вводятся у провайдера. Его размещённая форма уменьшает нашу область обработки карточных данных, но не отменяет наши обязательства по безопасности.

## Реальный статус

В коде сборки сохраняются доставка, самовывоз и предпочтение провайдера. На странице интеграций — ссылки и статус «не подключено». Это **не готовый платёжный адаптер**. Production-эквайринг не включён; договоров, счетов и реальных операций исследование не создавало. Подписку Polar этим изменением не отключаем; применимость Polar к самой SaaS-платформе остаётся отдельным вопросом.

Следующее действие: согласовать merchant-per-store сценарий с FreedomPay, получить sandbox, реализовать и проверить адаптер. Параллельно завершать независимые функции сайта, не выдавая отсутствие эквайринга за причину незавершённости конструктора или бронирования.
