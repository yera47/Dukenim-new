# Dukenim: направления витрин и проверка оплаты

Дата: 9 сентября 2026. Рабочее исследование, не завершённый аудит checkout и мобильного UX всех сайтов. Проверены открытые страницы и доступный текст навигации; мобильные скриншоты, карточки и прохождение корзины для каждого из 18 примеров ещё требуются. Приведённые ниже применения — наши проектные рекомендации, а не доказательство увеличения конверсии. Чужие фотографии, тексты и идентичность не копируем.

## Объём

Фактический источник поддерживаемых сфер: `src/lib/launch-verticals.ts`: одежда, косметика, готовая еда, цветы, дом, другие товары. Услуги и мероприятия не входят в регистрацию. Еда — готовые порции, не ингредиентный склад; цветы — готовые букеты, не рецептуры.

## Как превращать это в конфигурации

### Углубление: карточка, ассортимент и достоверность

Проверка открытых страниц 09.09.2026 расширяет таблицу выше. Мобильное поведение и фактическое оформление заказа не выводятся из HTML: эти части требуют отдельной браузерной проверки. Данные о конверсии перечисленных брендов отсутствуют; сравнение описывает устройство покупки, а не рейтинг продаж.

[Baymard, Ecommerce Filter UI](https://baymard.com/learn/ecommerce-filter-ui) связывает полезность фильтров с реальными характеристиками листинга и понятными названиями. Применение: поиск, сортировка цены, реальные категории/варианты, сброс и видимое число результатов. Это инженерная адаптация исследования, не доказанный прирост конверсии Dukenim.

В общем компоненте каталога реализованы локально эти базовые операции; они используются главной витрины/категориями и общим preview-renderer. Дополнительно убраны неподтверждённые автоматические «Хит/Новинка»: флаг продавца теперь означает «Выбор магазина». Наличие вычисляется из вариантов, прежняя цена видна лишь когда она выше текущей. Это базовый покупательский механизм, не18готовых конфигураций.

Остаются: PDP/корзина/мобильный проход каждого из18сайтов; Aesop category недоступна при текущем запросе; авторские пути и третий сценарий ещё требуют реализации. Обнаружено серверное ограничение: create_catalog_atomic разрешает только2темы на тариф. Добавление третьей кнопки без согласованной миграции сломало бы сохранение — такой UI не добавлен.

Не создавать 18 независимых копий. Общий renderer получает валидированную структуру: `vertical`, `salesApproach`, порядок разрешённых блоков, ссылки на реальные коллекции/SKU, оформление бренда. Смена подхода не меняет остатки, цены, заказы или merchant account.

Три понятных выбора: «Быстро найти товар», «Показать вашу коллекцию», третий — по сфере («Подобрать уход», «На семью», «Подарок по случаю», «Собрать комплект»). AI объясняет рекомендацию ассортиментом и покупателями, не случайной палитрой. Предпросмотр и публикация используют те же компоненты. Эти конфигурации пока НЕ реализованы этим исследованием.

Для всех: карточка содержит реальную цену, фото, доступность и выбор варианта; checkout раскрывает доставку до подтверждения. Для одежды нужны размеры, косметики — состав/объём, еды — порция/аллергены, цветов — размер/замены/дата, дома — габариты. Не добавлять отсутствующие данные от имени продавца.

Мобильная гипотеза для проверки: две колонки товаров там, где остаётся читаемая цена; одна для сложных наборов; доступная корзина, горизонтальные короткие категории, никаких полноэкранных рекламных видео поверх покупки. Это требования к нашему продукту, НЕ проверенные наблюдения мобильных версий всех источников.

## Kaspi: подтверждённое и неизвестное

[Официальный Kaspi Гид](https://guide.kaspi.kz/partner/ru/pos/payments/remote/q2020) прямо описывает самостоятельный ввод суммы покупателем и уведомление кассиру в POS. [Получение ссылки](https://guide.kaspi.kz/partner/ru/pos/payments/remote/q2019): ссылка отдельная для точки продаж. Предоставленный владельцем URL не проверен живой оплатой; web-fetch не открыл страницу. Скриншот соответствует описанию Гида.

Публичного подтверждения параметра фиксированной суммы для этой ссылки не найдено. Это НЕ доказательство отсутствия других договорных API Kaspi. Параметр `amount` не добавляем. API заказов маркетплейса и локальная Smart POS интеграция не являются автоматически API оплаты корзины Dukenim.

Рекомендуемое подключение требует ответа Kaspi о доступном для независимых интернет-магазинов методе: server-created invoice/QR с суммой KZT, merchant identity, уникальным order reference, сроком действия и подтверждением через аутентифицированный status API/webhook. Точную схему, документы и комиссию нельзя выдумать до ответа провайдера.

Готовый текст запроса: «Мы Dukenim, SaaS-конструктор отдельных интернет-магазинов Казахстана. Каждый продавец получает деньги на собственный Kaspi Pay, мы не собираем общий денежный поток. Нужен счёт на фиксированную сумму корзины с привязкой к заказу, проверкой статуса, отменой и возвратом. Доступна ли официальная web-интеграция для такой модели? Какие требования к продавцу, договору, API, sandbox, подписи уведомлений и документам? Обычная ссылка с ручным вводом нам не заменяет эту интеграцию». Не отправлено и договор не заключён.

Временный режим допустим только с явным ручным подтверждением продавца в POS: серверный итог и номер заказа рядом со ссылкой конкретного магазина. Возврат браузера или скриншот покупателя не меняет статус на paid. Ссылка владельца не становится общей настройкой всех tenants.

## Polar: важный риск совместимости

[Действующая политика Polar от 25.03.2026](https://polar.sh/legal/acceptable-use-policy) перечисляет физические товары, marketplaces/продажу чужих товаров и продукты, позволяющие другим продавцам продавать, среди запрещённых категорий. AI tools требуют дополнительной проверки. Поэтому не использовать Polar как эквайринг товаров. Даже применимость подписки SaaS-конструктора к нашей модели нужно письменно уточнить, а не предполагать разрешённой только потому, что технически checkout работает. Действующие настройки не изменены.

## Последующая проверка исследования

### Независимые UX-основания

[Baymard: число полей важнее числа шагов](https://baymard.com/blog/checkout-flow-average-form-fields) поддерживает сокращение воспринимаемых усилий checkout. Применение к нашему onboarding — гипотеза, не прямой результат исследования конструктора: группировать связанные вопросы, не показывать ненужные поля и не обещать магическое фиксированное число шагов.

[Baymard: обзор применённых фильтров](https://baymard.com/blog/how-to-design-applied-filters) описывает проблемы ориентации без видимых выбранных фильтров. Поэтому мобильный ассортиментный шаблон должен показывать выбранные фильтры и удаление каждого, а не прятать всё в меню. Это не значит, что фильтры нужны магазину с тремя товарами.

### Уточнённый путь заявки Kaspi

[Официальная инструкция, обновлённая17.08.2026](https://guide.kaspi.kz/partner/ru/payments/distributor/connection/q4389): партнёр Kaspi Pay подаёт заявку на сотрудничество с сервисом «Платежи», менеджер сообщает результат в течение5рабочих дней. Это канал выяснения доступности нужного API, не обещание автоматического одобрения Dukenim. Для каждого продавца нужны собственные merchant-реквизиты; дополнительные документы и схема интеграции определяются Kaspi. Мы заявку не отправляли, юридические согласия не принимали.

- Для каждого сайта ещё открыть одну категорию, карточку и доступный checkout без отправки заказа; снять desktop/mobile и записать конкретные наблюдения.
- Расширить независимую UX-проверку на карточки/ошибки checkout; не объявлять эти бренды самыми конверсионными.
- Реализовать конфигурации, затем проверить preview/public equivalence и покупку. Таблица ссылок сама по себе не закрывает требование.
